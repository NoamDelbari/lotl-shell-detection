# Chapter 8.4 — The hybrid behavioural cascade: does the architecture earn its complexity?

> `report/ch8_4_cascade_findings.md` is generated by `analysis/ch8_4_cascade.py`
> and reports what the cascade *scores*. This chapter reports what each stage
> *does*, using the per-stage audit in `analysis/ch8_4_cascade_forensics.py`
> (`results/ch8_4_cascade_forensics.json`), which fits the two component models
> once and then derives every routing variant from the cached stage-1 anomaly
> scores and stage-2 probabilities. The routing rule is deterministic given
> those two arrays, so the ablations below are exact reproductions of
> `CascadeDetector.predict_with_trace`, not re-runs with different seeds.

## The verdict first

The cascade is the architecture the assignment recommends: a cheap unsupervised
filter clears obvious benign traffic, a supervised model classifies the rest,
and an LLM arbitrates the residue. We built it, measured it, and it does not
work — not marginally, and not for the reason we expected.

| Dataset 1 (n = 3,049) | F1 | precision | recall | FPR | tn / fp / fn / tp |
|---|---:|---:|---:|---:|---|
| XGBoost-hybrid alone | **0.8761** | 0.8755 | 0.8766 | 0.0415 | 2192 / 95 / 94 / 668 |
| stage 1 + 2 (no arbitration) | 0.8737 | 0.8760 | 0.8714 | 0.0411 | 2193 / 94 / 98 / 664 |
| stage 2 + 3 (no pre-filter) | 0.8716 | 0.9088 | 0.8373 | 0.0280 | 2223 / 64 / 124 / 638 |
| **full three-stage cascade** | **0.8685** | 0.9083 | 0.8320 | 0.0280 | 2223 / 64 / 128 / 634 |

| Dataset 2 (n = 1,915) | F1 | precision | recall | FPR | tn / fp / fn / tp |
|---|---:|---:|---:|---:|---|
| XGBoost-hybrid alone | **0.8482** | 0.8508 | 0.8455 | 0.0494 | 1365 / 71 / 74 / 405 |
| stage 1 + 2 (no arbitration) | 0.8463 | 0.8535 | 0.8392 | 0.0481 | 1367 / 69 / 77 / 402 |
| stage 2 + 3 (no pre-filter) | 0.8415 | 0.8830 | 0.8038 | 0.0355 | 1385 / 51 / 94 / 385 |
| **full three-stage cascade** | **0.8396** | 0.8863 | 0.7975 | 0.0341 | 1387 / 49 / 97 / 382 |

The ordering is identical on both corpora and it is the worst possible one:
**every stage we add to the supervised model makes the system worse, and the
full cascade is the weakest configuration of the four.** Removing stage 1
improves it. Removing stage 3 improves it. Removing both — which is to say,
deleting the cascade and shipping the single model — improves it most.

The cascade's one apparent win is precision: 0.9083 against the hybrid's
0.8755 on Dataset 1, with the false-alarm rate falling from 4.15% to 2.80%.
That is a 33% relative reduction in analyst workload from false positives, and
it is the number a charitable write-up would lead with. The rest of this
chapter is the argument for why it should not.

## Attributing every error to the stage that caused it

Because the pipeline is a sequence of overrides on the supervised model's
verdict, each stage's contribution to the confusion matrix can be isolated
exactly. Relative to the hybrid running alone:

| dataset | stage | false alarms removed | true detections destroyed |
|---|---|---:|---:|
| D1 | stage 1 — Isolation Forest clears | −1 | −4 |
| D1 | stage 3 — arbitration on the band | −30 | −30 |
| D1 | **net** | **−31** | **−34** |
| D2 | stage 1 — Isolation Forest clears | −2 | −3 |
| D2 | stage 3 — arbitration on the band | −20 | −20 |
| D2 | **net** | **−22** | **−23** |

The precision gain is real and it is bought at an exchange rate of **1.10
missed attacks per false alarm avoided on Dataset 1, and 1.05 on Dataset 2.**
For an intrusion-detection system that is the wrong side of one-for-one. A
defender who genuinely valued analyst time at that rate would not need a
cascade to express the preference; the following two sections show they already
have a cheaper way to express it.

## Stage 1: a filter that clears almost nothing and costs more than it saves

The first stage is an Isolation Forest whose clearing threshold is calibrated,
not fixed: `CascadeDetector.fit` sets it to the 1st percentile of the *training
attacks'* anomaly scores (`src/ensemble.py:52-60`), so that 99% of known
attacks by construction survive to stage 2. The calibrated values are 0.003333
(D1) and 0.003245 (D2).

Three measurements follow.

**It clears 6.8% of Dataset 1 and 4.3% of Dataset 2** — 207 and 83 commands.
The generated results file already flags the mechanism behind this: a threshold
set for recall cannot also be set for throughput, and this operating point
deliberately buys the former. But the size of the resulting saving is worth
stating plainly, because the analyst-fatigue argument is the entire
justification for having an unsupervised first stage at all. A filter that
removes one command in fifteen before the expensive model runs is not a
meaningful reduction in compute, and it removes almost no analyst work either:
of the 207 commands it clears on Dataset 1, the hybrid would have raised an
alert on five.

**The recall guarantee does not quite survive contact with held-out data.**
Calibrated for 99% retention on the training attacks, stage 1 retains 98.82%
of Dataset 1's test attacks and 98.54% of Dataset 2's — it silently discards 9
and 7 real attacks respectively. The gap is small and in the expected
direction, but it is the honest number: a threshold fitted on training attack
scores generalises to roughly 1.2–1.5% attack loss rather than the 1.0%
budgeted.

**Its marginal effect on the confusion matrix is negative on both corpora.**
Of the 9 attacks it discards on Dataset 1, 5 would have been missed by stage 2
anyway; the marginal damage is 4 lost detections. Against that it removes
exactly **1** false alarm the hybrid would have raised. Dataset 2 is the same
story: 3 detections destroyed, 2 false alarms removed. This is the cascade's
premise inverted — the pre-filter is supposed to absorb benign noise cheaply,
and instead it is a small net drain that happens to fall on the wrong class.

Chapter 8.1 explains why this was foreseeable. On Dataset 1 the Isolation
Forest catches **zero** attacks the Random Forest misses — its false negatives
are a strict superset — while its false positives are near-disjoint from the
supervised models' (Jaccard 0.056). Its only useful signal in this project is
about *benign* traffic, which is precisely the role stage 1 assigns it. The
finding here is that even in the one role its error structure suits, it is too
weak to pay for itself.

## Stage 3: an arbitrator that never fires, and a threshold shift wearing a costume

Stage 3 routes commands whose stage-2 probability falls in [0.35, 0.65] to an
arbitrator. The live arbitrator is a Llama-3.1-8B call (`huggingface_arbitrator`);
the figures above use the deterministic offline stub that lets the harness run
without a token (`src/llm_triage.py:75-93`), which labels a command malicious
if it matches one of six hard LotL motifs — `/dev/tcp`, `nc -e`, `bash -i`,
`curl … | sh`, `wget … |sh`, `base64 -d` — and benign otherwise.

On the 146 Dataset-1 commands routed to it, **the stub fired zero times.** On
Dataset 2's 101, it fired twice. It is, on this band, a constant classifier
that returns "benign".

This is not bad luck; it is structural. Thirty-nine Dataset-1 test commands
match one of the six motifs and **all thirty-nine are attacks** — which is
exactly why the supervised model is already confident about them, and exactly
why not one of them lands in the [0.35, 0.65] uncertainty band. The stub's rule
set and the router's selection criterion are anti-correlated by construction:
the commands it can recognise are the ones stage 2 never asks it about, and the
commands it is asked about are the ones no keyword rule resolves. Its coverage
on the test sets is 1.3% and 0.2% of traffic; its coverage on the traffic it is
actually shown is 0% and 2%.

The consequence is that stage 3, as run, is not arbitration at all. Forcing an
entire probability band to "benign" is arithmetically identical to moving the
decision threshold from 0.50 to 0.65 for those rows. Every one of the cascade's
30 avoided false alarms and 30 missed attacks on Dataset 1 is that threshold
shift, relabelled.

## The dominance test

If the cascade's operating point is a threshold shift, a threshold should be
able to reach it. We swept stage 2's decision threshold from 0.05 to 0.95 in
0.01 steps and asked how many single scalar values match or beat the full
cascade on **both** precision and recall:

| dataset | cascade (P / R / F1 / FPR) | best single threshold on stage 2 | thresholds dominating the cascade |
|---|---|---|---:|
| D1 | 0.9083 / 0.8320 / 0.8685 / 0.0280 | t = 0.65 → 0.9088 / 0.8373 / 0.8716 / 0.0280 | **3** (t = 0.65, 0.66, 0.67) |
| D2 | 0.8863 / 0.7975 / 0.8396 / 0.0341 | t = 0.66 → 0.8863 / 0.7975 / 0.8396 / 0.0341 | **1** (t = 0.66) |

On Dataset 1, `p ≥ 0.65` beats the three-stage cascade on precision, on recall
and on F1 at an identical false-alarm rate, and `p ≥ 0.67` beats it on all
three while also running cleaner (FPR 0.0258). On Dataset 2 the match is not
merely close — `p ≥ 0.66` reproduces the cascade's confusion matrix to four
decimal places on every headline metric.

> **An Isolation Forest, an XGBoost-hybrid and an LLM arbitrator, wired into a
> three-stage routing architecture, produce an operating point reachable by
> changing one `>=` comparison in the single model they contain.** And if the
> objective is F1 rather than precision, the best single threshold — 0.53 on
> D1, 0.52 on D2 — beats the cascade by 0.98 and 0.89 points while requiring
> no second model, no third stage and no inference calls.

This is the finding of Chapter 8.4, and it is a negative one. It does not
depend on the stub's weakness being fixed: it is a statement about what the
*architecture* delivered, measured against the cheapest possible alternative
rather than against no alternative at all.

## What the routing does get right — and the ceiling it implies

One component survives, and it matters for the bonus chapter.

The router — "send stage 2's low-confidence band to a second opinion" — selects
exactly the right rows. Attack prevalence inside the band is **0.411** (D1) and
**0.386** (D2) against 0.250 overall, so the band is enriched for attacks
rather than being a pocket of ambiguous noise. More tellingly, the hybrid's own
accuracy on the band is **58.9%** and **63.4%**, against **95.6%** and **94.1%**
on everything outside it. The router is a working detector of the strong
model's blind spot: it isolates 4.8% of traffic on which the project's best
model is barely better than a coin flip.

That gap is worth something to whoever can close it. Substituting a *perfect*
arbitrator on the band — an oracle, as an upper bound rather than a claim —
gives:

| dataset | hybrid alone | full cascade (stub) | cascade with oracle arbitration |
|---|---:|---:|---:|
| D1 | 0.8761 | 0.8685 | **0.9132** |
| D2 | 0.8482 | 0.8396 | **0.8849** |

A flawless second opinion on 4.8% / 5.3% of commands is worth **+3.7 F1 points**
over the best single model on both corpora. That is the headroom the live LLM
layer is competing for, and it is the number the bonus chapter should be scored
against — not against zero.

It also fixes the bar. The stub's accuracy on the band is 58.9% / 63.4%, which
is *precisely* stage 2's own accuracy on the same rows; its 60 and 42
overrides split 30/30 and 21/21 between helping and hurting. An arbitrator that
does not beat the model it is overriding is strictly a latency cost, and the
offline stub does not. A live arbitrator must clear 58.9% (D1) and 63.4% (D2)
accuracy on these specific commands before routing to it is defensible at all —
a lower bar than it sounds, since these are the rows a keyword rule and a
gradient-boosted tree both find genuinely hard, but a real one, and one the
bonus chapter must measure rather than assume.

## What should ship

Three recommendations follow from the measurements, and the report makes them
rather than presenting the cascade as a success.

1. **The three-stage cascade should not be the deployed configuration.** The
   single XGBoost-hybrid at a tuned threshold dominates it on both corpora. If
   the deployment values precision over recall, that preference is expressed by
   the threshold, where it is visible, auditable and free — not by an
   architecture that expresses it accidentally.
2. **Stage 1 should be dropped from the cascade, not re-tuned.** Its recall
   calibration and its throughput saving are in direct conflict, and at the
   recall-safe end of that trade-off it clears too little to matter while still
   discarding 9 and 7 real attacks. Chapter 8.1's finding that the Isolation
   Forest's false negatives are a strict superset of the Random Forest's is the
   structural reason: it has no independent view of the attack class to
   contribute.
3. **The routing rule should be kept and the arbitrator replaced.** The band is
   the most valuable 5% of traffic in this project — a well-identified pocket
   where the best available model is near-chance — and the oracle bound says a
   competent second opinion there is worth more than any model swap measured
   anywhere else in Chapter 6.

The general lesson is one the chapter should state directly, because it
generalises past this project: a multi-stage architecture must be evaluated
against the strongest single-stage configuration of its own components, at a
tuned operating point. Evaluated against nothing, this cascade looks like a
33% reduction in false alarms. Evaluated against one `>=` comparison, it is a
regression.
